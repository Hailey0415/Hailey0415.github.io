## 2. How the website was created

The initial site was built from the candidate's verified profile, academic CV materials, research record, and the portrait supplied by the user. The process was:

1. Consolidate public-safe facts from `../CANDIDATE_PROFILE.md` and the user's confirmed instructions.
2. Organize the public narrative around academic identity first: short introduction, research fields, education, publications and working papers.
3. Place conferences, internships, government work, teaching-adjacent activity, and public engagement in a secondary News section.
4. Create a restrained blue-green visual system in `styles.css`, with a responsive desktop/mobile layout.
5. Build the site as a Quarto project and verify it locally with `quarto render` and browser inspection.
6. Create the GitHub user-site repository `Hailey0415/Hailey0415.github.io` and push the source to `main`.
7. Configure GitHub Pages to deploy through the workflow in `.github/workflows/publish.yml`.
8. Refine the site after visual review, including direct PDF navigation for CV, a working visible email link, removal of the Methods block, updated policy-brief wording, and additions to professional/public-engagement history.

The design principle is academic, concise, and evidence-based. Research and education lead; projects, internships, government secondments, conferences, and public engagement support the main academic narrative rather than compete with it.

## 4. Source-of-truth and content rules

- Use `../CANDIDATE_PROFILE.md` as the main factual source. Never invent dates, affiliations, publication status, authorship, job titles, policy impact, or confidential details.
- When the user supplies a new confirmed fact, update `CANDIDATE_PROFILE.md` as well as the relevant public page when the fact is intended for publication.
- Keep the personal website URL in the top contact block of every future CV/Resume: <https://hailey0415.github.io/>.
- Before publishing a changed paper status or author list, resolve the known conflicts documented in `../AGENTS.md` and `../CANDIDATE_PROFILE.md`.
- For confidential work, follow the user's latest explicit public wording and the disclosure limits in the profile. Do not expose internal titles, proof letters, official identities, or instruction text without explicit permission.
- Maintain the current hierarchy: academic background and research are primary; professional/public engagement is secondary.
- Keep Research entries concise. Use full links only where the user has approved them; otherwise show keywords without adding unverified URLs.
- Do not add a custom domain, paid hosting, analytics, trackers, or third-party services unless the user explicitly requests them.

## 5. Standard maintenance workflow

Run commands from the website directory:

```bash
cd "/Users/haileyliu/Desktop/求职/personal-research-website"
```

### Step 1: Inspect before editing

```bash
git status --short --branch
git log --oneline -5
```

If the working tree contains unrelated user changes, preserve them and avoid overwriting them. When network access is available and no local work would be disrupted, synchronize safely with:

```bash
git pull --ff-only origin main
```

### Step 2: Edit source files only

Edit the relevant `.qmd`, `_quarto.yml`, CSS, image, or PDF source file. Do not edit files inside `_site/`; Quarto overwrites them on the next render.

Typical updates:

- Homepage text, education, or links: `index.qmd`
- Publications, working papers, keywords, or policy brief: `research.qmd`
- Conferences, internships, or public engagement: `news.qmd`
- Navigation, footer, global metadata, or CV target: `_quarto.yml`
- Colors, spacing, typography, responsive behavior: `styles.css`
- CV replacement: overwrite `files/Hailey_Yuhan_Liu_NYUAD_Academic_CV.pdf` with the approved PDF while keeping the filename
- Portrait replacement: overwrite `images/portrait.jpg` with the approved image and then check cropping on desktop and mobile

### Step 3: Render and preview locally

Render the full site:

```bash
quarto render
```

For interactive review:

```bash
quarto preview
```

The preview command prints a local URL. Open it in a browser and inspect About, Research, News, the CV link, and both desktop and mobile widths. Stop the preview process when finished.

### Step 4: Review the exact change

```bash
git diff --check
git diff
git status --short
```

Confirm that only intended source files changed. Because `_site/` is ignored, a successful local render should not add generated HTML to the commit.

### Step 5: Commit and upload through GitHub

```bash
git add <changed-files>
git commit -m "Describe the website update"
git push origin main
```

The remote uses the user's GitHub repository. The push relies on the Git credentials already configured on the computer; do not place credentials in commands or files.

### Step 6: Verify automatic deployment

After the push:

1. Open the repository's **Actions** tab: <https://github.com/Hailey0415/Hailey0415.github.io/actions>.
2. Confirm that the latest **Publish Quarto website** run finishes successfully for both build and deploy jobs.
3. Open <https://hailey0415.github.io/> and verify the live change.
4. Open the direct CV URL if the PDF changed: <https://hailey0415.github.io/files/Hailey_Yuhan_Liu_NYUAD_Academic_CV.pdf>.
5. If the browser shows an older version immediately after a successful deployment, wait briefly and reload without cache before diagnosing a failure.

## 7. GitHub Pages and deployment logic

The workflow file is triggered by either a push to `main` or a manual run. It performs two jobs:

1. **Build**: check out the repository, install Quarto, run `quarto render`, and upload `_site` as a Pages artifact.
2. **Deploy**: publish that artifact to the repository's GitHub Pages environment.

Required workflow permissions are already declared in `.github/workflows/publish.yml`: read repository contents, write Pages, and request an identity token. If deployment stops working, first inspect the latest Actions log and the repository's **Settings → Pages** configuration. The publishing source should remain GitHub Actions.

For a fresh computer, clone the repository and enter it before editing:

```bash
git clone https://github.com/Hailey0415/Hailey0415.github.io.git
cd Hailey0415.github.io
```

Git and Quarto must be installed locally for rendering. GitHub Actions remains responsible for the production build, so a local `_site/` folder never needs to be uploaded manually.

## 8. Safe recovery and rollback

- If a render fails, read the first relevant Quarto error, fix the source file, and run `quarto render` again before pushing.
- If GitHub Actions fails, inspect whether the failure occurred during checkout, Quarto setup, render, artifact upload, or deploy. Fix the source or workflow and push a new commit.
- If a published change must be undone, prefer a reversible Git commit:

```bash
git log --oneline -10
git revert <commit-id>
git push origin main
```

- Do not use destructive history rewriting or delete the repository to fix a content error.
- Do not rename the repository unless the public URL is intentionally being changed; the default GitHub Pages address depends on the `Hailey0415.github.io` repository name.
